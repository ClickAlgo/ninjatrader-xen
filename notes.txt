Implement isolated build diagnostics logging for Xen, initially focused on NinjaTrader build and repair requests.

## Primary objective

Add a diagnostic logging subsystem that records build outcomes and detailed compiler failures so we can investigate why NinjaTrader generations fail and improve prompts, RAG retrieval and repair behaviour.

This feature must be implemented with minimal changes to existing Xen logic.

## Critical isolation requirement

Treat diagnostics as an observational subsystem only.

Do NOT refactor, rewrite or restructure the existing:

* build pipeline
* repair pipeline
* AI/model request logic
* prompt construction
* RAG retrieval
* compiler logic
* project/version logic
* credit/billing logic
* user-facing responses

Existing behaviour must remain unchanged when diagnostics are disabled.

Prefer adding new dedicated classes/services/files and introducing only the smallest integration hook required to capture the result of an existing build or repair operation.

If logging itself fails for any reason, the Xen build/repair request must continue normally.

Diagnostics must never cause a user request to fail.

## Configuration

Add configuration settings similar to:

```json
"BuildDiagnostics": {
  "Enabled": true,
  "StoreSuccessfulSource": false,
  "StoreFailureSource": true,
  "StorePrompt": true,
  "RetentionDays": 90
}
```

Use the project's existing configuration conventions rather than creating a parallel configuration system.

When:

```text
Enabled = false
```

diagnostic database writes should not occur.

## Database design

Use the application's existing database technology, ORM, migration system and naming conventions.

Create an appropriate schema based around these entities.

### BuildDiagnosticRun

Store one lightweight record for each NinjaTrader build or repair attempt.

Suggested fields:

```text
Id
CreatedUtc
Platform
TaskType
Model
ProjectId
RequestId
AttemptNumber
Success
DurationMs
InputTokens
OutputTokens
RagUsed
RagDocumentIds
RagSimilarityScores
FinalOutcome
```

Adapt field types and nullable values to the existing application architecture.

Do not create dependencies on values that the current pipeline does not already expose.

### BuildDiagnosticFailure

Create a detailed failure record only when a build/repair fails.

Suggested fields:

```text
Id
BuildDiagnosticRunId
UserPrompt
GeneratedSource
PreviousSource
ModelResponse
RepairAttempt
FailureClassification
CreatedUtc
```

Use relationships/foreign keys consistent with the existing database design.

### BuildDiagnosticCompilerError

A build may contain multiple compiler errors, so store compiler errors as child records rather than a single combined text field.

Suggested fields:

```text
Id
BuildDiagnosticRunId
ErrorCode
Message
Line
Column
```

For example:

```text
CS0103
The name 'DashStyleHelper' does not exist in the current context
```

## Failure classification

Support a classification field but do not introduce complex classification logic into the build pipeline.

Initial values may include:

```text
MissingNamespace
InvalidOverload
UnknownMember
InvalidType
LifecycleError
BarsAgoError
PropertyError
DrawingApiError
OrderApiError
MultiSeriesError
Unknown
```

It is acceptable for new failures to initially use:

```text
Unknown
```

We can improve classification later.

Do not use another AI request merely to classify an error.

## RAG diagnostics

Where this information is already available from the current RAG pipeline, record:

```text
RAG document IDs
RAG similarity scores
```

This is important because we need to distinguish between:

1. The required knowledge was not present in RAG.
2. The knowledge existed but was not retrieved.
3. The correct document was retrieved but the model ignored it.
4. The model applied the RAG information but another error occurred.

Do not change RAG retrieval behaviour as part of this task.

Only observe and record existing retrieval information.

## Successful builds

Successful builds should create only the lightweight BuildDiagnosticRun record.

By default:

```text
StoreSuccessfulSource = false
```

Do not store large generated source files for successful builds unless the configuration explicitly enables this.

## Failed builds

For failures, store the diagnostic information required to investigate the problem, subject to the configuration settings.

Where available, capture:

* task type
* model
* original user request
* generated NinjaScript
* previous source for modify/repair operations
* compiler error codes
* compiler messages
* compiler line/column
* repair attempt number
* RAG documents retrieved
* RAG similarity scores
* model response
* final success/failure outcome

Reuse existing data already available in the pipeline. Do not duplicate expensive processing merely for diagnostics.

## Security and privacy

Before persistence, protect against obvious sensitive values appearing in prompts or code.

Do not log:

* API keys
* authorization tokens
* passwords
* connection strings containing credentials
* secrets already identified by existing application security/redaction utilities

If the application already has secret-redaction functionality, reuse it.

Do not build a large new security framework as part of this task.

## Retention

Add support for:

```text
RetentionDays
```

Structure the implementation so old diagnostic records can be deleted according to this setting.

If the application already has an appropriate scheduled cleanup/background maintenance mechanism, integrate with it using the existing pattern.

Otherwise implement the cleanup service/repository method but do not introduce a new background framework solely for this feature.

Deleting a BuildDiagnosticRun must correctly delete its associated failure/compiler-error records using the project's preferred cascade or explicit deletion approach.

## Performance

Diagnostics must have negligible impact on normal Xen requests.

Do not add additional AI calls.

Do not add additional compilation.

Do not repeat RAG searches.

Do not serialize or store large successful source files by default.

Database logging failures must be caught and handled internally so diagnostics cannot break the primary operation.

Use the existing application's logging mechanism to record an internal warning if diagnostic persistence fails.

## Architecture

Prefer an isolated structure similar to:

```text
BuildDiagnostics/
    BuildDiagnosticOptions
    IBuildDiagnosticService
    BuildDiagnosticService
    BuildDiagnosticRun
    BuildDiagnosticFailure
    BuildDiagnosticCompilerError
    repository/data configuration as appropriate
```

Follow the existing project's architecture and naming conventions rather than forcing this exact folder structure.

The existing build/repair pipeline should ideally need only a very small call such as:

```csharp
await buildDiagnosticService.RecordAsync(...);
```

or an equivalent pattern appropriate to the current codebase.

Do not scatter diagnostic-specific logic throughout existing services.

Build the diagnostic payload inside the diagnostics subsystem wherever practical.

## Integration rule

Before changing existing code:

1. Inspect the complete current build and repair flow.
2. Identify the narrowest point where the required result data already exists.
3. Hook diagnostics into that point.
4. Do not move existing logic merely to make diagnostics easier to implement.
5. Preserve existing execution order and behaviour.

If build and repair have separate completion paths, use a shared diagnostic service rather than duplicating persistence logic.

## Scope

Implement the database entities, configuration, persistence service, required migrations and minimal integration required to start collecting diagnostics.

Do not create an admin dashboard or reporting UI in this task.

The database should, however, be structured so we can later query:

* total builds
* first-pass success rate
* final success rate after repair
* errors grouped by compiler error code
* failures grouped by model
* failures grouped by task
* failures grouped by RAG document
* most common failure classifications
* individual failure details

## Backwards compatibility

Existing Xen behaviour must be unchanged.

Specifically verify:

```text
Diagnostics disabled -> existing behaviour
Diagnostics enabled and DB write succeeds -> existing behaviour + diagnostic record
Diagnostics enabled and DB write fails -> existing build/repair behaviour continues
```

Do not make diagnostic persistence part of a transaction whose failure could roll back a project, build, credit operation or other existing user action.

## Implementation quality

Keep the implementation simple and maintainable.

Avoid speculative abstractions.

Avoid broad refactoring.

Do not change unrelated code formatting.

Do not rename existing classes, methods or database entities unless absolutely necessary.

Do not modify existing business logic merely to improve code style.

* repair entry point
